01 / Recommended direction

A separate web app, under your domain.

Put an Open Tlamatini entry on xaiht.org. It opens rc.xaiht.org, where users sign in, choose a linked computer and enter their Tlamatini account.

1

The website is the front door

XAIHT provides navigation and sign-in. The RC application has its own browser origin, security policy and container deployment.

2

Your PC makes the connection

Tlachihuani opens an outbound connection to a public relay. Both home broadband and mobile data can reach that relay.

3

Your PC keeps control

The local Remote-Controller checks the approved phone, account and action. A website login alone does not authorize commands.

Users do not configure IP addresses, router ports, certificates or terminal commands. They make a one-time account/device connection on the PC. Normal use is sign in → choose computer → use Tlamatini. Adding a shortcut to the phone home screen is optional convenience, not an additional security guarantee.

If your Tlamatini configuration uses an external model or tool provider, that provider still receives the data needed for its existing function. Phone-to-PC encryption does not turn cloud inference into local inference or remove those recipients.

Publishing static client files is only one part of this work. We also need identity linking, a computer directory, a relay, an outbound PC connector and an authenticated remote session protocol. The cloud must never expose the entire intranet or turn into a general command runner.

05 / “The same account as Tlamatini”

One experience, an explicit account link.

The public website cannot safely infer that a local account named “angela” belongs to the website user Angela. We link the two once, with proof on both sides. The local password stays on the PC.

Recommended identity design

Use a maintained OIDC provider/broker for the XAIHT identity layer. Federate Google so existing site users can keep their familiar sign-in, and offer passkeys through the selected provider.

Both website and RC use their own Authorization Code + PKCE flow, exact redirects, state and nonce. The provider's session gives SSO; application cookies remain separate.

Provider selection is open. Reusing Google OIDC directly in two independently validated clients is a simpler alternative; claim stability, app registration and future provider migration must still be explicit.

Existing users are not silently migrated

The website currently has Google OAuth and its own custom session, not a shared OIDC issuer for Tlamatini. Harden/migrate that entry point deliberately.

Link the existing local account after local authentication and consent. Record issuer and subject. Re-authenticate before linking a second identity provider; matching email alone is never an account merge. OIDC pairwise subject values can differ between website, native and RC client registrations. The central broker or an explicit authenticated account-link table must normalize those registrations; never assume raw subject strings are identical across clients.

A name change does not break the link. Account deletion, ownership transfer and recovered identity never silently recreate deleted device grants.

The result for Angela: sign in to XAIHT, see AngysLap, and open the explicitly linked English or Spanish account. She does not retype a local Tlamatini password into a public website. The identity mapping follows OpenID Connect's stable-identifier rules.

06 / One-time setup

One wizard on the PC. One approval for a new phone.

Setup should be a guided product feature, not a collection of administration tabs. It should expose meaningful choices and perform the mechanical steps automatically.

Engineering contract for a safe, simple setup wizard
  • Use a standard native-app authorization flow with PKCE and verified loopback callback, or a provider-supported device authorization flow when appropriate. A cloud login callback never directly approves a local device. Review RFC 8252 and the phishing risks in RFC 8628.
  • The PC generates installation keys locally. Keep connector authentication keys, endpoint session identities and update-signing trust separate. Do not send private keys to the cloud.
  • Bind setup transaction, installation key, local account, edition, cloud principal, requesting device key and requested scopes. Changing any of these restarts consent.
  • Invitation target: single-use, 5-minute expiry, at least 128 bits of entropy, bounded attempts. The QR includes the intended HTTPS origin and an authenticated PC-key commitment. Consume atomically. A short fallback entry code is rate-limited and requires the same local approval.
  • Keep invitation secrets out of query/access logs, referrers, screenshots uploaded by support and analytics. A fragment-carried secret is removed from browser history immediately after reading, sent only to its fixed enrollment endpoint, and is not treated as independent trust in the delivered website code.
  • Do not request camera permission merely to paste or type a code; camera use is optional. Offer accessible manual setup. Expired or canceled setup starts cleanly without duplicate grants.
  • Local approval compares a cryptographically bound short confirmation, not a browser-provided friendly name. Never use a generic “a device wants access” approval that could approve a different pending transaction.
  • Startup availability is an explicit, initially off choice. Explain service startup separately from Windows sign-in and the XT launch broker. No power-plan change, Windows auto-login, router rule or firewall exception is made silently.
  • A recovery/login event at the identity provider cannot enroll a new browser. A new device needs local approval; delegated approval by an existing device is a separate future policy, not implicit in v1.
07 / Everyday connection

What happens after “Open Tlamatini.”

Cloud admission

The BFF keeps OAuth tokens server-side. The phone holds an opaque, host-only session cookie. A state-changing request obtains a short-lived route to one computer; exact Origin and CSRF defenses apply.

Bind each route/admission ticket to the validated cloud principal, installation, opaque account binding, requesting device key, protocol/profile, nonce and expiry, with atomic single-use consumption. It grants no command scope. For a browser WebSocket, authenticate using the same-origin session plus a one-use, connection-bound admission message. Never place long-lived bearer tokens in a WebSocket URL. Before admission, allow only a small first frame and a short timeout.

Local authorization

The PC verifies the pinned peer identity, local device grant, account, edition, permission generation and session freshness. Each operation checks the current grant again.

Cloud/relay messages cannot change the destination account after the protected session is established. An attacker who can reroute a stream should trigger authentication failure, not control another computer.

Reconnecting is not re-executing. If the phone changes from Wi-Fi to mobile data, establish fresh session keys and ask for the existing operation receipt. Do not automatically resend chat, Stop, Start or an execution approval just because the acknowledgment was lost.

08 / Security design and its limits

HTTPS protects the route.
Endpoint encryption protects the content.

A normal HTTPS reverse proxy decrypts traffic at the cloud server. For this design, the protected phone-to-PC session is an additional inner layer: the relay forwards it without needing its plaintext or traffic keys.

There is a real product decision here. The existing approved design requires ML-KEM-1024, ML-DSA-87 and independently trusted client distribution. A normal website or installed PWA cannot independently protect its own code from replacement by the server that publishes it. This document does not silently relax that requirement.

Client optionExperience and protectionRelease position
Hosted web application / PWAOpen rc.xaiht.org directly. Can protect payloads from a relay that only forwards encrypted traffic, provided the delivered client code is trustworthy. A compromised publishing origin can replace JavaScript, read decrypted data and issue actions as the user.Matches the requested website experience. Needs explicit acceptance of hosted-code trust before enabling this alternative remote profile; not approval granted by this design request.
Independently signed mobile clientShares the RC interface and account flow, but bundles the renderer, consent UI, protocol and trust roots in a verified install/update channel. The website can offer Open in Tlamatini RC.Recommended route if retaining the stronger independent-client requirement. Requires a separate mobile packaging/distribution project.
Mutable web UI + “crypto helper” onlyThe website still sees plaintext and can ask the helper to authorize malicious requests. It does not protect the command approval experience.Insufficient for the strict requirement.

Passkeys protect sign-in; they do not make arbitrary same-origin JavaScript trustworthy. Non-exportable browser keys prevent normal key export, not misuse by an injected script. SRI, CSP, a service worker and signed manifests improve defenses but do not create an independent verifier when the same origin can replace that verifier. W3C WebCrypto security considerations describe these limits.

The required cryptographic engineering gate

Use ML-KEM-1024 for the required post-quantum key-establishment component and ML-DSA-87 for the required signature component, in a maintained, reviewed protocol and implementation. Those algorithm names alone are not a secure session protocol. NIST FIPS 203 and FIPS 204 define the algorithms, not this application's complete transport.

Must be specified and independently reviewed

  • Mutual peer authentication, PC identity pinning, device approval and transcript binding.
  • Key confirmation, directional authenticated encryption, nonce uniqueness and replay counters.
  • Forward-secrecy properties, ephemeral key handling, rekey limits and key erasure.
  • Hybrid construction if selected, with an approved combiner and explicit failure behavior.
  • Protocol version binding and refusal of downgraded or unsupported profiles.
  • Recovery, identity rotation, multi-tab state and crash-safe counter/key handling.

Must be proven before Internet release

  • Maintained library availability, licensing, dependency review and test vectors.
  • Native PC and supported mobile interoperability, including memory/performance limits.
  • Handshake tampering, replay, downgrade and cross-account substitution resistance.
  • Trusted client updates with rollback protections and offline root-key recovery.
  • Independent protocol and implementation review; no hand-written crypto design passed off as a standard.
  • Clear fail-closed UI: “Update required for secure remote access.” No silent classical fallback.

Specific protocol/library choice remains open. The earlier inner-TLS-over-WebSocket idea is a candidate only. It may be selected only if it satisfies the exact suite, peer trust and mobile implementation requirements. Until then, production remote mode stays unavailable.

AI does not remove the need for conventional security boundaries. Strong authentication, narrow permissions, signed updates, endpoint hardening and clear revocation reduce exposure. They cannot promise invulnerability if the phone, Windows PC or trusted client publisher is compromised.

09 / Permission model

Signing in is not permission to control a PC.

After a permission change, increment the grant generation, close affected sessions and cancel or deny pending authorizations as appropriate. Device revocation must stop further dispatch and streaming. An already completed external side effect cannot be undone by revoking its session.

Typed request contract and idempotency

The relay transports messages, not commands selected by arbitrary strings. The local dispatcher supports an explicit versioned allowlist such as application.status, application.start, application.stop, conversation.submit, conversation.cancel, conversation.history and conversation.permission.

Bind protected requests to session ID, installation ID, local binding ID, device/grant generation, operation ID, deadline and schema version. Permissions derive from stored local policy, never from a client-supplied scope list. No browser-provided executable, PID, Windows service name, shell string, host, port or arbitrary filesystem path is executable authority.

An identical idempotency key and payload returns the same durable receipt; a changed payload conflicts. Preserve accepted → executing → completed/failed/canceled/outcome unknown distinctions. A submitted request is not success. A pending tool approval names the exact request and cannot be replayed for another operation.

10 / Conversation, downloads and the full workspace

Carry the polished RC experience across the relay.

Rich conversation

Keep the main application's prepared response HTML and the RC sanitizer. Preserve cards, headings, tables, code and execution reports. User messages remain literal; a model's HTML cannot become trusted navigation, permissions or scripts.

Progress/events and complete responses travel inside the protected channel. The existing complete-response limit of 8 MiB is an initial compatibility ceiling, not a reason to load every response at once.

Save file / Guardar archivo

Retain account/message-owned manifests, exact artifact identity, size and SHA-256 validation. Files travel from the PC to the phone inside the protected stream. The cloud does not need a public download URL or plaintext copy.

Keep the current 64 MiB ceiling initially; tune downward for mobile memory if measured. File-content integrity is verified before claiming a download can start.

  • Preserve Unicode filenames and extensions. Show progress, cancellation and useful retry errors in English and Spanish.
  • Download behavior on mobile Safari/Chrome may use a download list, Files app or share sheet. Do not promise an arbitrary device path or that tapping Save has completed a user-facing OS save dialog.
  • Do not cache API responses, decrypted chat, tickets or downloaded files in the service worker. Once the user saves a file, it belongs to the phone's storage/backup policy and cannot be remotely “unsaved.”
  • Expired or app-restart-invalidated tickets are renewed by reloading eligible history. Changed files need a new attachment. Legacy artifacts without trusted manifests must be regenerated.
  • Revoke/cancel closes the stream. Disconnect discards incomplete in-memory content. Large resumable transfers require an authenticated range/chunk protocol and reauthorization; they are not assumed in the first release.

The full mobile workspace needs a separate isolation design. Today's local proxy can serve main-app HTML and scripts. Putting every PC's active HTML under rc.xaiht.org/workspace/... would give that code the same origin as all RC credentials. Different paths are not isolation.

First public feature set

Compact RC: conversation, history, execution consent, monitoring, authorized Start/Stop, verified downloads and scoped schedules. Hide unavailable features instead of showing a broken Full workspace button. Audio remains unavailable until separately implemented and tested.

Full workspace follow-on

Adapt the app to an isolated document/origin or rebuild its views against typed remote APIs. For active HTML, require per-session origin or opaque sandbox isolation, no shared RC cookies/device keys, a narrow authenticated message bridge and an encrypted asset/API transport.

No arbitrary intranet proxy. Exact route/method/size allowlists, CSRF semantics, active-content isolation and account boundaries must pass review. Current cookie/network assumptions will need changes; merely rebasing URLs is insufficient.

“Offline” must never become a dead end.

Startup, shutdown and schedules

Preserve the current installation default: Remote-Controller is Manual and stopped. A new explicit availability option may configure SCM automatic startup and XT sign-in startup after explaining the difference and obtaining the necessary local elevation. Opening XT alone never starts services. Do not enable Windows auto-login or modify sleep settings automatically.

The outbound connector is a component of Tlachihuani.RemoteController, not a separate agent that can silently revive remote access. Stopping RC closes remote connections and suspends its scheduler. It does not stop Tlamatini or Torrenter. The ordinary phone UI offers Disconnect and account/device controls; service maintenance remains a local administrative operation.

Schedules remain durable on the PC. Recheck scope, grant generation and the original scheduling policy before dispatch. Explicitly define missed-run behavior and show it to users. No cloud backlog of chat/stop/consent requests. Connection loss follows the existing authorization-watchdog and cancellation rules; “cancellation requested” is distinct from confirmed cancellation.

12 / Hosting and containers

Deploy beside the site, with independent ownership.

The website repository documents a GCP Compute Engine VM, NGINX HTTPS, Docker/systemd, Cloud SQL and a Jenkins/Artifact Registry delivery path. That is useful infrastructure precedent, not a verified inventory of the current production environment.

Container and delivery requirements
  • Pin release images by digest. Separate image, secrets, database role and deployment identity for RC from the website. Use a supported runtime; select dependency versions during implementation rather than inventing pins in this design.
  • Run non-root with read-only root filesystems where possible, dropped capabilities, resource limits and application-owned writable mounts. No host networking, privileged mode, mounted Docker socket or unnecessary host paths.
  • Keep secrets in the hosting platform's secret manager. TLS renewal, identity-provider keys, connector registration keys and client update-signing keys have separate ownership and rotation plans.
  • NGINX/load balancer must support WebSocket upgrades and long-lived streams. Set an explicit heartbeat and idle timeout across every hop. The repository's current NGINX helper uses a 60-second read timeout, so it cannot be copied without checking the connection design. NGINX's official WebSocket guide describes this behavior.
  • Start with proposed 20-second heartbeats, 60-second stale leases and at least 90-second proxy idle allowance, then tune from real mobile/proxy measurements. Reconnect uses exponential backoff with jitter; do not synchronize all PCs after an outage.
  • Limit pre-auth connections, frame sizes, per-device streams, per-account bandwidth and aggregate memory. Apply backpressure instead of buffering whole large responses in the relay. Disable WebSocket compression for secret-bearing mixed content unless reviewed.
  • Validate WebSocket Origin, authentication, session expiry and message schemas; keep rate limits for the life of the connection. Edge WAFs cannot inspect encrypted inner commands, so local validation is mandatory. OWASP WebSocket guidance.
  • Build signed provenance/SBOM and immutable release manifests, review dependency vulnerabilities and reproduce asset hashes. No Snyk use in this project. Stage and canary before public rollout; never deploy a floating “latest” image.
  • Use readiness/liveness separately. During deploy, stop new admission, drain bounded existing sessions, then reconnect clients to a healthy relay. Do not restart the website just to deploy RC.

Scale by evidence

For an internal pilot, one RC host plus a private metadata database is enough to measure. For a public availability objective, use at least two failure domains/instances, a redundant metadata store and documented relay routing. A connected PC belongs to a relay owner/lease; use short-lived rendezvous tickets to connect its phone to that same relay. Failover establishes new sessions and reconciles receipts.

N × r

Relay egress model

For N active sessions delivering an average r bytes/second, forwarded user data contributes roughly N × r egress, plus protocol overhead. Measure total directional traffic and provider billing separately.

Bounded

Memory model

Active streams × fixed buffer budget + connection overhead. Large file size must not multiply unbounded relay buffers.

Measure

No invented monthly price

Choose region, traffic assumptions, retention and availability first. Then estimate compute, database, outbound bandwidth, identity and operations costs.

Generic tunnel or VPN products are alternatives for administrator-operated access. They can solve reachability but do not automatically deliver this account model, local grants or the exact end-to-end post-quantum requirement. See the outbound-connector pattern in Cloudflare Tunnel documentation; no such provider is selected or enabled here.

Record relationships, key rotation and initial time budgets

CloudPrincipal(issuer, subject) → ComputerLink(installation_id, owner_id, revision) → AccountLink(opaque_binding_id, edition, local_account_uuid) → DeviceGrant(device_key_id, scopes, generation) → ProtectedSession(session_id, lease, profile). Foreign-key/tenant predicates and unique constraints enforce ownership. Any account/device deletion writes a revocation tombstone; backup restore cannot roll the security generation backward unnoticed. Device and installation keys rotate by proof of the existing key or new local approval; no “click through” identity replacement warning.

Proposed initial budgets: route ticket ≤60 seconds and single-use; invite ≤5 minutes; unauthenticated first frame ≤5 seconds; connector lease 60 seconds with 20-second heartbeats; local operation authority revalidated at least as strictly as the current watchdog; sensitive scope edits require recent sign-in. Browser-session idle/absolute expiry and step-up thresholds are separate configurable policies, selected during the identity implementation. These are design defaults to test, not measured guarantees.

Prompt injection / tool misusePreserve account tool restrictions and exact execution approvals; remote grants do not create extra tool authority.Chat can operate tools. Network security does not make an unsafe model/tool policy safe.
Old backup / downgraded softwareSecurity generations, revocation tombstones, minimum accepted versions, signed monotonic update policy.Ambiguous restored identity state fails closed and requires reconciliation; never resurrect revoked devices automatically.
15 / Running and recovering the service

Build the operational controls before publishing.

Observe without collecting conversations

Measure admitted connections, failed handshakes, lease age, reconnect frequency, queue/buffer pressure, per-route bytes, relay saturation and latency. Use opaque correlation IDs to trace an operation across hops without logging its prompt.

Redact authentication headers, cookies, invitation secrets, file tickets, protected payloads and filenames. Operator dashboards should explain health without exposing local accounts to unrelated support staff.

Minimal retention, deliberate backups

Back up identity-link metadata and security state with encryption and restricted access. Do not back up chat/file payloads in the cloud because they are not stored there. Define retention periods before launch; proposed operational metadata retention is 30 days, subject to product/privacy review.

Restores must reconcile local revocation generations before reconnecting devices. If security continuity is uncertain, require renewed local approval.

Lost phone and account recovery

From the PC, remove the device immediately. From a recovered cloud account, reject new cloud routing to that device immediately and retain the denial until the PC acknowledges it. Force-close active relay sessions and propagate revocation to the PC. Local enforcement is bounded by propagation and the authorization lease, not instantaneous across a partition: the PC fails closed when that lease cannot renew, and rechecks before new dispatch. Already-running or completed external actions cannot be promised undone.

Cloud recovery restores sign-in, not the lost device's private key or local grant. A replacement phone follows the one-time approval flow.

Incident response

Provide global and per-account deny controls, key-rotation procedures, signed update withdrawal and a status page independent of the failing control plane. Preserve minimal audit evidence.

The main application’s Disable this account’s remote access revokes that binding’s grants and sessions while preserving other linked accounts. An explicit global XT Disable remote access for this computer or Stop Remote-Controller closes the connector for every account. Local Tlamatini and independent Torrenter remain usable.

Upgrade and rollback rules

Use a published client/server protocol compatibility window. The public shell can update faster than the PC; unsupported combinations show an explicit update message. Do not let a service worker retain an incompatible or revoked shell indefinitely. Cache only immutable public shell assets, never session/API responses.

Connector updates use the normal signed Tlachihuani installer/update path. The cloud cannot push arbitrary binaries or script commands through the connector. Prepare database changes with reversible metadata migrations where possible; security revocations are monotonic and must not be undone by application rollback.

For a strict signed mobile client, code and trust-root updates require independent signature verification, expiry/revocation handling and rollback protection. A malicious online publisher cannot select a new root on its own. Hardware-backed support for the exact PQ private keys must be evaluated; do not assume OS keystores directly support every algorithm.

Usability target

After one-time setup, reach a ready conversation with sign-in plus at most one computer selection. No repeated pairing in a known browser.

Reliability target

Every submitted action is attributable to a durable receipt. Uncertain outcomes are shown explicitly and never converted to silent retries.

Security target

No cloud account or website role alone can expand local authority. Unsupported security profiles fail closed. No arbitrary intranet tunnel.

18 / Decisions and evidence

What is decided here, and what needs a later choice.

Recommended architectural decisions

  • rc.xaiht.org as a separate application origin.
  • Independent RC containers and production host identity.
  • Outbound PC connector over443, owned by Remote-Controller.
  • Opaque relay plus authenticated endpoint protection.
  • OIDC identity linking; no local password sync.
  • Local device grants and typed actions remain authoritative.
  • Compact sanitized RC first; active workspace isolation separately gated.
  • Tlamatini execution stays on the PC; Torrenter stays independent.

Choices before implementation/release

  • Keep strict independent-client distribution, or explicitly approve the hosted-browser trust profile as an additional option.
  • Reviewed PQ protocol/library and mobile trusted-client packaging.
  • OIDC provider/broker, passkey/recovery policy and site-account migration.
  • Cloud region, measured scale, availability target, retention and operating budget.
  • Startup availability defaults beyond the preserved Manual/off installation default.
  • Full-workspace scope and isolation solution.

These are design decisions to discuss later. This document does not ask users to make these choices during daily connection.
